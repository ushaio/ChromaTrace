# 思考指南

> **目的**：把思路撑开，接住那些你原本没想到的情况。

---

## 为什么要有思考指南

**大多数 bug 和技术债来自「没想到这一层」**，而不是能力不足：

- 没想到层边界上会发生什么 → 跨层 bug
- 没想到代码模式在重复 → 到处是重复实现
- 没想到边界情况 → 运行时崩溃
- 没想到后来接手的人 → 读不懂的代码

这些指南的作用是帮你**在动手写代码之前先问对问题**。

## 速查：思考触发器

### 什么时候该想跨层问题

- [ ] 功能触及 3 个以上层（前端 / IPC / Rust 命令 / 磁盘）
- [ ] 数据在层与层之间**换了格式**
- [ ] 同一份数据有多个消费方
- [ ] 你不确定某段逻辑该放在哪一层
- [ ] 你在新增一种事件类型、一条 JSONL 记录、一个 IPC 载荷字段、或一个配置项
- [ ] UI / 命令层开始直接对原始载荷字段做类型断言

→ 去看 [跨层思考指南](./cross-layer-thinking-guide.md)

### 什么时候该想代码复用

- [ ] 你正在写的代码跟某处已存在的东西很像
- [ ] 同一个模式出现了 3 次以上
- [ ] 你在往多个地方同时加同一个字段
- [ ] **你在改任何常量或配置**
- [ ] **你在新建工具函数 / 辅助函数** ← 先搜一遍！
- [ ] 两个文件各自对同一个未类型化的载荷字段做本地断言
- [ ] 多个分支根据 `kind` / `action` 更新同一份派生状态

→ 去看 [代码复用思考指南](./code-reuse-thinking-guide.md)

### 什么时候该核实 AI 交叉评审的结论

- [ ] 评审说「用户输入可能被恶意构造」→ 先查真实数据来源（内部清单？用户配置？外部 API？）
- [ ] 评审说「缺少校验」→ 这份数据来自可信的内部来源吗？
- [ ] 评审说「行为变了」→ 读代码注释——这是不是有意设计？
- [ ] 评审说「测试里有 bug」→ 在脑子里把被测功能删掉——测试还过吗？还过 → 这是同义反复的测试

**AI 评审常见的误报模式**：

1. **信任边界混淆**：把内部数据（随包分发的 JSON 清单）当成不可信的外部输入
2. **无视设计注释**：把代码注释里已说明的有意行为当成 bug 上报
3. **变量误读**：没把变量追到真正的定义处（例如 Map 的键到底是路径还是名字）

**核实铁律**：每一条 CRITICAL / WARNING 结论，在排优先级之前都必须回到真实代码里核实。给 AI 评审预留约 35% 的误报率。

## 改动前置铁律（关键）

> **改任何值之前，先搜一遍！**

```bash
# 搜一下你正要改的这个值
grep -r "要改的值" .
```

就这一个习惯，能挡掉绝大多数「忘了同步改 X」的 bug。

## 这个目录怎么用

1. **动手前**：把相关的那份指南扫一眼
2. **写的过程中**：觉得某处重复或者绕，就回去翻指南
3. **踩坑之后**：把新领悟补进对应的指南（从错误里学）
