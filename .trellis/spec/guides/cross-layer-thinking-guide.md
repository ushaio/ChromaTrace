# 跨层思考指南

> **目的**：动手实现之前，先把数据跨层流动的路径想透。

---

## 问题在哪

**大多数 bug 出在层的边界上**，不在层内部。

常见的跨层 bug：

- 某一层返回格式 A，下一层期望格式 B
- 存的时候是 X，中间层转成 Y 时丢了数据
- 多个层各自实现了同一段逻辑，实现方式还不一样

---

## 实现跨层功能之前

### 第一步：把数据流画出来

```
来源 → 转换 → 落盘 → 读取 → 转换 → 显示
```

对每一个箭头都问：

- 这里的数据是什么格式？
- 可能出什么错？
- 校验由谁负责？

### 第二步：认出边界

| 边界 | 常见问题 |
|------|----------|
| 前端 ↔ IPC（`invoke`） | 类型不匹配、字段缺失、`Result<T, String>` 被当成成功值 |
| Rust 命令 ↔ 磁盘 / 系统凭据 | 路径归一化、编码、权限、中断后留下的半成品 |
| 前端 ↔ 模型 API | 序列化、图片重编码、超时与部分响应 |
| 组件 ↔ 组件 | props 形状变化 |

### 第三步：把契约定下来

对每个边界明确：

- 输入的确切格式是什么？
- 输出的确切格式是什么？
- 可能出现哪些错误？

---

## 常见的跨层错误

### 错误 1：隐式的格式假设

**坏**：不确认就假设某个字段的格式（日期、路径分隔符、颜色空间）。

**好**：在边界上做显式格式转换。

### 错误 2：校验散落各处

**坏**：同一个东西在多个层各校验一遍。

**好**：在入口处校验一次。

### 错误 3：抽象泄漏

**坏**：组件知道磁盘目录结构或凭据存储的实现细节。

**好**：每一层只认识它的邻居。

> 本项目的对应做法：`src/lib/desktop.ts` 是唯一的 IPC 边界（组件不直接 `invoke`），`src/lib/types.ts` 是唯一的跨模块类型出口。

### 错误 4：每个消费方各自解析同一份载荷

**坏**：命令层读到原始载荷后就地做断言：

```typescript
const thread = (ev as { thread?: string }).thread;
const labels = (ev as { labels?: string[] }).labels;
```

看起来是局部的，但这意味着**每个消费方都私藏了一份自己对契约的定义**。下次字段一变，改了一个命令，漏了另一个。

**好**：在边界处解码一次，然后导出带类型的投影：

```typescript
if (!isThreadEvent(ev)) return false;
return ev.thread === filter.thread;
```

**规则**：对于 append-only 日志、JSON 流、RPC / IPC 载荷、配置文件，以下四件事各自只能有一个所有者：

- 事件 / 载荷的类型定义
- 从 `unknown` 出发的类型守卫与归一化
- UI 与命令层使用的元数据投影
- 从事实来源重放状态的 reducer

渲染代码可以格式化字段，但**不得重新定义载荷契约**。

## 跨层功能清单

动手前：

- [ ] 完整的数据流已经画出来
- [ ] 所有层边界都已识别
- [ ] 每个边界的格式已定义
- [ ] 校验发生在哪一层已确定

实现后：

- [ ] 用边界情况测过（null、空、非法值）
- [ ] 每个边界的错误处理都已核实
- [ ] 数据往返一圈后没有损耗
- [ ] 消费方是 import 共享解码器 / 投影，而不是就地断言载荷字段
- [ ] 派生状态指回源头的事件标识（`seq`、`id`、`version`），而不是自己另造一套游标

## 什么时候该写流程文档

出现以下情况就写：

- 功能横跨 3 个以上层
- 涉及多个团队 / 多个人
- 数据格式复杂
- 这块以前出过 bug

## 事件日志与投影的边界

append-only 日志本身就是跨层契约。同一个事件要穿过：

```
输入 → 写入方 → 日志文件 → 读取方 → 过滤 → reducer → 显示
```

### 清单：新增一种事件类型或字段之后

- [ ] 把新的事件类型加进中心化的事件分类表
- [ ] 在事件层加上带类型的变体或类型守卫
- [ ] 为来自用户输入 / JSON 的数组、对象字段补归一化函数
- [ ] `seq` / `id` 的赋值只留在写入方
- [ ] 过滤器与 reducer 消费带类型的事件守卫，而不是本地断言
- [ ] 显示代码消费 reducer 输出或带类型事件，而不是原始 JSON
- [ ] 至少补一条回归，证明「历史重放」和「实时过滤」用的是**同一套**过滤模型

## 附录：以下内容仅适用于 Trellis 上游仓库，本项目不适用

> 保留原文以便与上游对照；**读到这里可以直接跳过**。这几节讲的是 Trellis 自己 monorepo 里的模板一致性、文档版本路由与 CLI 模式探测。
>
> ⚠️ **上游模板缺陷（已在本项目中处理）**：Trellis 0.6.17 分发的这份模板里，下面三节内容**被完整重复了两遍**（逐字相同）：`Cross-Platform Template Consistency`、`Generated Runtime Template Upgrade Consistency`、`Mode-Detection Probe Checklist`。本文档已去重，只保留一份。如果你在别的项目里也看到重复，那是上游模板的问题，不是你的项目被污染了。

### 跨平台模板一致性

Trellis 的命令模板（例如 `record-session.md`）在**多个平台**存在，内容相同或近乎相同，这是一条跨层边界。

改完任何命令模板后：

- [ ] 找出所有含同一命令的平台：`find src/templates/*/commands/trellis/ -name "<command>.*"`
- [ ] 更新所有平台副本（Markdown `.md` 与 TOML `.toml`）
- [ ] Gemini 的 TOML 要适配续行（`\\` 与 `\`）和三引号字符串
- [ ] 跑 `/trellis:check-cross-layer` 确认没有漏

**真实案例**：改了 Claude 侧的 `record-session.md` 用 `--mode record`，忘了 iFlow、Kilo、OpenCode、Gemini——被跨层检查抓出来。

### 生成型运行时模板的升级一致性

有些生成文件既是文档又是运行时输入。在 Trellis 里，`.trellis/workflow.md` 会被 `get_context.py`、`workflow_phase.py`、SessionStart 过滤器和每轮 hook 解析。改这类模板必须在「全新 init」和「升级」两条路径上都验证。

改完任何被运行时解析的模板后：

- [ ] 列出**所有**读取该模板的运行时解析器，而不只是安装它的写入方
- [ ] 检查相关语法是否落在 tag 块之类的显式托管区域之外
- [ ] 验证全新 `init` 的输出，以及一个会写入旧 `.trellis/.version` 的 `update` 场景
- [ ] 用旧版原始模板 fixture 加一条升级回归，断言安装后的文件能达到当前打包形态
- [ ] 更新拥有该运行时契约的后端 spec

**真实案例**：Codex inline 模式把工作流的平台标记从 `[Codex]` / `[Kilo, Antigravity, Windsurf]` 改成了 `[codex-sub-agent]` / `[codex-inline, Kilo, Antigravity, Windsurf]`。全新 init 是对的，但 `trellis update` 只合并 `[workflow-state:*]` 块，托管区域之外的旧标记被原样保留。结果：升级过的项目拿到了新 hook 脚本，却还是旧的工作流路由，`get_context.py --mode phase --platform codex` 可能返回空的 Phase 2.1 详情。

### 文档版本边界

带版本号的文档本身就是一条跨层边界：源码路径、`docs.json` 的版本路由、以及渲染出来的版本选择器，三者必须描述同一条发布线。

改带版本的文档之前：

- [ ] 确认目标发布线：stable / beta / RC
- [ ] 核实所编辑的 MDX 路径与该发布线一致：
  - stable：`docs-site/{start,advanced,...}` 与 `docs-site/zh/{start,advanced,...}`
  - beta：`docs-site/beta/**` 与 `docs-site/zh/beta/**`
  - RC：`docs-site/rc/**` 与 `docs-site/zh/rc/**`
- [ ] 核实 `docs.json` 的导航把版本标签指向同一批路径
- [ ] 提交前在另一棵树里 grep 该发布线专属的术语
- [ ] 把「beta 内容出现在根发布路径下」当成**源码路径 bug**，不是渲染 bug

**真实案例**：一个仅属于 beta 的任务流程改动，把 `prd.md` + `design.md` + `implement.md`、任务创建同意、Codex 模式横幅写进了根目录的 `start/` 与 `advanced/` 路径。于是文档站会在 Release 选择器下展示 0.6 beta 的行为。修复方式是恢复根发布文档、把 0.6 的内容移到 `beta/` 与 `zh/beta/`，并加一道针对根发布树的 beta 标记 grep 审计。

### 模式探测清单

当 CLI 通过探测远端资源来自动判定模式时（例如探测 `index.json` 是否存在来决定「走市场下载」还是「直接下载」）：

实现前：

- [ ] 探测要在**所有**会用到该结果的代码路径里都执行（交互式、`-y`、各种 `--flag` 组合）
- [ ] 区分 404 与瞬时错误——不要把两者都当成「不存在」
- [ ] 瞬时错误要**中止或重试**，绝不能静默切换模式
- [ ] 上下文变化时（例如用户切换了源）**重置**共享状态（缓存、预取数据）
- [ ] **快捷路径**（例如 `--template` 跳过选择器）必须与被探测路径有同等的错误处理质量——检查下游函数别再调那种一网打尽的包装器

实现后：

- [ ] 把从探测结果到模式判定分支的每条路径都追一遍——不能有穿透
- [ ] 外部格式契约（giget URI、裸 URL）要么有测试，要么至少在注释里写明
- [ ] 元数据读取要么消费完整响应，要么用流式解析器——**绝不**把固定长度的前缀当完整 JSON 解析
- [ ] 从解析出的片段重建复合标识符时，核实**所有**字段都在、且**位置正确**（例如 `provider:repo/path#ref` 而不是 `provider:repo#ref/path`）
- [ ] 核实快捷路径之后调用的**动作函数**内部没有沿用旧的一网打尽式抓取——在错误区分有意义的地方必须用探测级别的版本

**真实案例**：自定义 registry 流程在 3 轮评审里累计 8 个 bug：(1) 探测只在交互模式跑；(2) 瞬时错误穿透到错误模式；(3) giget URI 的 `#ref` 位置错了；(4) 预取模板在切换源时泄漏；(5) `--template` 快捷路径绕过了探测，但 `downloadTemplateById` 内部仍用一网打尽的 `fetchTemplateIndex`，把超时变成了「模板不存在」。

**真实案例**：Agent session 的更新提示用 `response.read(4096)` 抓 npm `latest` 元数据，然后当完整 JSON 解析。`@mindfoldhq/trellis` 的包元数据超过 4 KB，JSON 被截断、解析静默失败，于是首次会话注入里看不到更新提示。修复：解析前读完整响应，并补一条 `version` 后面跟 8 KB 元数据尾巴的回归。
