**已验证的现状**（读自 `src-tauri/src/`，尚未上升为规则）：

- crate 用 `log` 门面，后端实现是 `tauri_plugin_log`。
- 插件**只在 debug 构建里注册**：
  ```rust
  if cfg!(debug_assertions) {
      app.handle().plugin(
          tauri_plugin_log::Builder::default()
              .level(log::LevelFilter::Info)
              .build(),
      )?;
  }
  ```
  **release 构建里没有安装任何 logger**，因此所有 `log::*` 调用都被静默丢弃。不要把日志当成用户可见的诊断信息。
- 目前用量极小：全仓只有两处 `log::warn!`，都在 `asset_library.rs`（`"skip unreadable dir {:?}: {error}"` 和另一处），都是「非致命、跳过该项继续」的场景。
- crate 里**没有任何 `println!` / `eprintln!`**。
- 面向用户的失败走 `Err(String)`（见 [错误处理](./error-handling.md)），不走日志。日志是给开发者的，IPC 错误是给用户的。

需要团队拍板的问题：

1. 「只对跳过型的可恢复工作打 warn」是预期策略，还是要放宽（例如命令进出各打一条 `info`）？
2. release 构建要不要接一个日志后端（写文件），让用户能把诊断信息发回来？

## 不应记什么

<!-- 敏感数据、个人信息、密钥 -->

这一条没有商量余地，且当前的代码已经体现了：

**不要**记录 API Key、用户照片的完整本地路径、图片 EXIF、发往模型服务商的请求体。`asset_library.rs` 在失败时用 `{:?}` 记了一个*目录*——把那条当作**边界**，不要当成都这样记路径的许可。
